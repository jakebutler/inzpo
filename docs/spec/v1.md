## 1. Product overview

Inzpo is a **single-user, web-based design-inspiration vault**. Its one user is
the **Owner**: the library's only reader and writer. Auth exists to let the
Owner in and keep everyone else out (§9).

**Core value is rediscovery and filtering** — finding "that thing I saved" by
style × usage × medium × palette. The beautiful browsing Wall matters, but
filtering is the anchor; the Filter bar (§6) is the product's center of gravity.

Standing properties that shape every flow:

- **Deterministic automation first**: color extraction, metadata fetch, kind
  auto-guess — all mechanical, no AI/ML services in v1.
- **Mobile-friendly from day one** — mobile-friendly, not mobile-first. Every
  flow in this spec was verified at 390px (no horizontal scroll, ≥36px touch
  targets, sticky primary actions).
- **Cheap managed services**: the whole stack targets ~$0/month at single-user
  scale (§10).
- **Nothing depends on the outside staying reachable**: Source metadata, preview
  images, and article text are copied into the vault at capture (§3, §5, §8) —
  with the single live-render exception of platform video embeds (§5.7).

## 2. Item model

### 2.1 Six kinds, one identity space

Inzpo recognizes six kinds of Item: **URL, screenshot, photo, palette, article,
video**. Kind is **fixed at capture** — capture flows pre-select it via
detection with a one-tap override *before* Save (§5.2); there are no post-save
kind edits. "This is really a video" means capture again — cheap, because all
kinds share one identity space.

**Data model:** a single core `items` table (`id`, `kind`, `title`, `note`,
timestamps) with cross-cutting attachment tables — **not** polymorphic JSONB,
**not** per-kind tables. The decisive fact: uniform multi-value facet/tag
assignment (§4) references one item id, so all six kinds must share one
identity space. (ADR-0002.)

Conceptually the kinds are not six shapes but **three cross-cutting
attachments**, combined:

| Kind | Linked Source | Media asset | Colors |
|---|---|---|---|
| URL / Article / Video | ✓ (Source) | **preview** | – |
| Screenshot / Photo | – | **primary** | – |
| Palette | – | – | the substance itself |

### 2.2 Linked Source (URL / article / video)

The Source is the outside address the Item points at. Metadata — title,
description, poster — is **copied at capture** (poster bytes into R2 per §8),
then user-editable and **never re-fetched for display**. A failed fetch still
captures: **a bare URL is a valid Item**. The media table carries a mime type
so an uploaded-video slot exists later (files stay out of v1, §5.7).

### 2.3 Media assets: primary vs preview

One media table, two roles. A screenshot/photo Item carries at most one
**primary** asset — the substance itself. A linked Item carries a **preview**
(og:image copy / oEmbed poster), **user-replaceable** by upload. Consequences:

- **No albums or carousels in v1** — multi-image is multiple Items.
- Screenshotting a page already saved creates a **new** Item: an Item is one
  captured thing, not an evolving dossier.
- Extracted colors on image Items are derived, regenerable, **never
  hand-edited** (§8.3).

### 2.4 Palettes and Origin

A first-class **Palette** Item is user-owned: an ordered color list (≥1),
editable and nameable (full color editor, §7.4). "Save extracted colors as a
palette" **copies the values into a new Item — a snapshot, no live link** — and
stamps **Origin**: the only item-to-item link in v1, a directional pointer from
derived Item to source Item, shown on both. Deleting the Origin Item clears the
pointer; the palette keeps its substance. Origin means "derived from", **never**
"duplicate of" — a screenshot of an already-saved URL is not an Origin
relationship.

### 2.5 Validity, title, note

Per-kind minimums: URL required for linked kinds, a media asset for image
kinds, ≥1 color for palettes; all else optional. **Title** is optional and
auto-derived: fetched title → filename → first color hexes → "Untitled" —
always editable. Note optional everywhere.

### 2.6 Deletion

**Hard delete in v1** — one confirm, no trash, no undo. Deleting an Item
cascades: stored media files, facet/tag assignments, collection memberships.
Deleting a Collection never deletes its Items. Deleting an Origin Item clears
the link; derived Items survive.

### 2.7 Collections and Smart collections

A **Collection** is a manually curated, ordered group: many-to-many with an
explicit position per membership, name + optional description, cover derived
from a member Item at view time. Not an Item; carries no Facets. A **Smart
collection** is a saved live query (§6.6) — a separate entity and sidebar
sibling. Grouping in v1 is these two, full stop: the Filter bar is the
auto-group (§6.6).

## 3. Ontology: Facets, Vocabularies, Free tags

### 3.1 The six Facets — fixed in v1

| Facet | Boundary (per glossary) |
|---|---|
| **Style** | the design language |
| **Usage** | the intended use |
| **Medium** | the surface the design lives on |
| **Format** | the artifact's shape |
| **Mood** | the emotional read |
| **Complexity** | the visual information density |

The facet set is **not user-extensible in the v1 UI**; facets are stored as
data (not enum types) so post-v1 extension stays cheap. **Uniform multi-value**:
every Facet allows any number of values per Item — one rule, no per-facet
cardinality, no migrations when a facet "should have been" multi.

### 3.2 Vocabulary lifecycle

Values are **shared entities**: Items reference values, so rename and merge
cascade to every Item carrying them.

- **Create** — explicit rows in the vocabulary manager, and **create-on-type**
  while tagging during capture (§5.2).
- **Rename** — everywhere, immediate, global.
- **Merge** — ships in v1: pick 2+ values → 1 survivor, assignments move.
- **Delete** — only while a value is **unused** (button gated by live usage
  count, reason shown otherwise); everything else goes through merge.

**Seed vocabularies** (curated starter sets, fully editable; note the
deliberate coexistence of "minimal" in Style vs "sparse" in Complexity —
language ≠ density):

| Facet | Seeds |
|---|---|
| Style | minimal, brutalist, swiss, editorial, retro, futuristic, maximalist, organic |
| Usage | dashboard, landing page, pricing page, mobile app, e-commerce, portfolio, onboarding, email |
| Medium | web, mobile, print, motion, packaging, environmental, social |
| Format | poster, logo, icon set, banner, business card, typographic specimen, UI kit, layout |
| Mood | calm, energetic, moody, cozy, dramatic, whimsical |
| Complexity | sparse, airy, balanced, rich, dense |

**Propagation into saved queries:** smart collections store values by name, so
renames and merges **must rewrite stored filter states** rather than let
queries silently break. Removal is impossible while any Item carries the value.

### 3.3 Free tags

Free tags share the Filter bar (rendered as flat autocomplete, visually
distinguished from structured facet groups) and the Vocabulary lifecycle — but
live in their **own namespace**: a Free tag and a Facet value may share a name
without being the same thing. **Promotion**: a Free tag can be promoted into a
Facet value (target facet chosen; value name prefills with the tag, existing
values offered as one-tap reuse); every Item carrying the tag gains the value,
the tag dissolves, saved searches follow the move. Promotion reuses merge
mechanics — the escape hatch from tag-entropy into structure.

## 4. Capture

### 4.1 The Capture surface

One screen. A **smart bar** intake takes a pasted URL or an image (drag-drop on
desktop, tap-to-pick on phone); Inzpo detects what arrived. As soon as substance
exists, the **tag tray** appears with all six Facets **fully expanded** (no
accordion), multi-value chips, and Free tags with create-on-type — the adopted
capture prototype's A+C hybrid. **Zero-tag capture is fine**; Items can be
tagged later on the Item. A Palette quick-add rides the same screen (snapshot +
Origin, §2.4).

**Kind auto-guess + one-tap override before Save:**

- **Link intake** (share target and paste-URL alike — same smart bar):
  oEmbed match (YouTube/Vimeo et al.) → **Video**; article signal (og:type
  article / substantial extracted body text) → **Article**; otherwise → **URL**.
  The linked kinds split by substance: written content is an Article, a video
  is a Video, anything else worth visiting is a URL.
- **Image intake** → **Photo** by default (camera-roll origin), one-tap
  override to Screenshot; a filename hint (`screenshot…`) may refine the guess.

Override happens before Save, so "kind fixed at capture" holds. All flows are
mobile-verified at 390px: no horizontal scroll, ≥36px touch targets, sticky
Save.

### 4.2 Duplicate notice

When the intake's URL matches an existing Item's copied Source address, the
Capture surface shows a **non-blocking** "Already saved → View existing" notice
naming the existing Item. **Saving proceeds regardless** — a second screenshot
of a saved page can be a deliberate capture. Rules:

- Watches **URL-linked kinds only** (URL, article, video); photos/screenshots
  have no address to match.
- Addresses compare **normalized**: lowercase scheme + host, strip fragment,
  strip trailing slash, strip `utm_*`-style tracking params.
- **All retroactive dedup is post-v1**: a duplicates view, any merge-Items
  operation, perceptual image hashing. At single-user scale retroactive dedup
  is as likely to fight the Owner as help.

### 4.3 Post-capture destination

**Save re-arms the Capture surface in place** — identical on phone and desktop.
Reset is **total**: URL input, image, kind, facet selections, free tags all
clear; nothing sticks across saves. A transient toast (~4s) confirms and
carries a **View item** action into the Item detail view (§7.3). No undo in
the toast — Items are edited from the library. Saved Items live on the Wall;
the Capture surface never becomes an inbox. (If batch-tagging friction shows
up in real use, the fix is an explicit "apply these tags to my last N saves"
tool in the library — never implicit stickiness.)

### 4.4 Share target

The **Share target** is a third front door into the same first-class capture
flows — no new Item kinds, no new attachments.

- **PWA manifest + Level 3 Web Share Target in v1**: manifest declares URL
  params (`title`/`text`/`url`) **and** `files: image/*` (Level 2 comes free
  inside Level 3; the multipart POST file intake reuses the image-upload path).
  No PDFs/documents — no v1 kind carries them.
- **Platform support** (verified 2026-08 via MDN/caniuse): Chrome/Edge/Opera
  desktop, Chrome for Android, Samsung Internet 12+. **Safari on iOS/iPadOS:
  not supported at the platform level**; Firefox and macOS Safari too.
- **iOS story**: copy-paste into the smart bar is first-class, **plus a
  doc-only Apple Shortcut recipe** (Share sheet → open `…/capture?url=<shared
  url>`) landing on the same pre-filled capture page — zero new backend.
  Importable Shortcut files are post-v1.
- **One-shot capture page**: the incoming URL or image lands pre-filled in the
  smart bar; kind auto-guessed with one-tap override; tag tray fully expanded;
  **Save closes the share-target window immediately** — the re-arming
  post-capture flow (§4.3) does not apply to this path. When the `url` param
  is absent, shared text is scanned for the first `http(s)` URL.
- **Multi-image shares take the first image only** in v1 (an Item carries at
  most one media asset; batch capture belongs to §7).
- **Cold start with expired session must survive login**: the capture page
  survives the login round-trip and still opens with the shared URL/image
  pre-filled (§9.5).

### 4.5 Article depth: the Archived copy

At capture, an Article Item extracts a **readable copy** from the HTML already
fetched for metascraper (readability extraction — no extra network round-trip).

- **Storage**: sanitized HTML object at `items/{ulid}/article.html` in R2; key
  + byte size recorded in the DB (the DB stays the metadata source of truth);
  served through the authenticated media proxy (§9.4); covered by the existing
  deletion-by-prefix cascade.
- **Sanitization scope**: **text-level structure only** — headings, paragraphs,
  lists, blockquotes, emphasis, code, tables, and body links kept as links;
  images, iframes, scripts, styles stripped. (Inline images would be hotlinks —
  exactly the live dependence the vault exists to avoid; pulling every article
  image through the sharp pipeline is scope creep.) Plain text is rejected: it
  loses the structure that makes a design article readable.
- **Reading**: an inline reading section on the Item detail view — the
  Article's substance display with minimal typography, unaffected by the
  ✎ Edit toggle (which covers fields, not substance).
- **Editability & re-fetch**: the Archived copy is capture-time substance,
  **read-only in v1** — title, note, and copied Source fields stay the editable
  surface. No re-fetch action: a failed/blocked/paywalled/SPA fetch leaves a
  valid metadata-only Item (the §8.4 fallback); want the text, capture the URL
  again.
- **Search**: article body text stays **out of Text search in v1** — justified
  by reading, not search. Body indexing is a post-v1 possibility.
- **Cost**: ~$0 — KBs of text inside R2's free tier, extraction on
  already-fetched HTML, no new services.

### 4.6 Video depth: embed, not upload

- **Platform videos (YouTube/Vimeo) play in-app** via a **sandboxed
  cross-origin iframe** embed (oEmbed's `html`, rendered per its security
  note) in the Item detail view. This is the glossary's one live-render
  exception: the embed plays from the source **while it lasts**; the copied
  poster and link are what survive a dead video.
- **No raw video uploads in v1**; the media table's mime-type slot keeps the
  door open for v2. **No ffmpeg anywhere in v1** — no frame grabs; the preview
  slot is user-replaceable, which is the "different frame" escape hatch.
- **Posters**: a single poster = the copied oEmbed `thumbnail_url` run through
  the standard sharp → derivatives → palette pipeline (§8).
- **Non-platform video URLs**: auto-guess unchanged (no oEmbed/article signal
  → URL kind, one-tap override to Video available). A non-platform Video Item
  is link + whatever metascraper finds — no in-app playback, poster if
  `og:image` exists else placeholder.

## 5. The Wall and the Filter bar

### 5.1 The Wall

A single **full-width masonry field** under a **slim toolbar**: Text search
box, Filters button (with active-count badge), sort select (newest / oldest /
title A–Z / shuffle), and a **Saved popover**. Every kind appears under one
card shape; what varies is the substance the card shows. **Quick actions**:
hover-revealed on desktop (open / add-to-collection / open-source / more);
persistent ⋯ on touch. *Implementation note:* wall scaling
(virtualized/infinite scroll) is an implementation decision, not a product
one.

### 5.2 Filter bar semantics

The Filter bar is the one bar that scopes the Wall: **Text search, facet
selections, free tags, color swatches, and item kind**, acting together.

- **Any-of (OR) within a dimension**; **AND across dimensions**.
- **Tri-state negation in v1**: each value takes include / exclude / ignore.
  Items lacking any value for a Facet drop out when that Facet carries an
  include selection.
- **The active-filter chip row** — the browse prototype's core move: one chip
  per active selection (dimension label + value + ✓/≠), always on screen, tap
  to remove, Clear all at the end. Filter state never hides inside a sheet.
- **Filter sheet** (bottom sheet on phone): Kind, the six facet groups, free
  tags, and the 14 fixed color swatches; tap = include, second tap = exclude
  (≠, strikethrough), third = off. The Done button shows a live
  **"N items match"** count.

### 5.3 Color dimension

**Color** is a filter dimension alongside the Facets, not a Facet. The swatch
picker offers a fixed **14-family color taxonomy**: red, orange, yellow,
cream/beige, brown, gold, green, teal, blue, purple, pink, black, white, gray.
No user-maintained vocabulary; the set is fixed in v1, and later additions are
cheap because mapping is deterministic. Every color an Item carries — an
image's extracted colors or a Palette's color list — maps to a family, and an
Item **matches a family when any carried color maps to it** (node-vibrant's ~6
swatches all count; no dominance weighting in v1). One rule for all kinds — no
per-kind special cases in the query model. Swatch selections take the same
tri-state stance as facet values.

### 5.4 Text search

**Text search** is plain **case-insensitive substring** matching — no
operators, quotes, or relevance ranking (single user, thousands of items:
predictable beats ranked). Its reach: titles, notes, facet values, free tags,
copied source titles/descriptions, and source URLs. **Article body text is out
of reach in v1** (§4.5). One text query ANDs with everything else, composing
inside saved queries like any dimension.

### 5.5 Sorts

**Newest first (default), Oldest, Title A–Z, Shuffle** (re-rolled per page
load — inspiration-wall behavior). No manual Wall ordering: Collections remain
the only hand-ordered thing in Inzpo.

### 5.6 Collections, Smart collections, the Saved popover

The **Saved popover** holds both:

- **Smart collection** = the Filter bar, saved: stores the **complete
  filter-bar state** — facet selections (tri-state), free tags, color
  swatches, item kind, text query — **plus a sort**. Nothing more expressive:
  the bar *is* the query language, so saving a search adds zero new
  semantics. Created via "Save this search" from the Wall's current state;
  edited by loading its state back into the bar, changing, saving. The query
  **runs fresh** on every view; membership order is its saved sort, never
  hand-ordering. Live match counts shown per saved search. Rename/delete lives
  in the Saved popover: rename changes only the saved query, delete never
  touches Items.
- **Collection** = a scope the bar operates within, applied from the same
  popover; filters apply within the scope.

Grouping in v1 is these two, full stop — **no auto-group-by-facet-value
entity**: selecting a facet value *is* the group, saving it *is* a smart
collection. Rendering results sectioned by a facet value would be display, not
structure. Nested collections, board layouts, and gallery views are post-v1
(map: out of scope).

### 5.7 Item detail view

A **full-screen page with back** — the capture toast's View-item destination.
Shows: the substance (media asset / Archived copy reading section / video
embed / palette colors), title/kind/captured date, note, the copied **Source**
box (with open-source action), colors with their families, facet groups, free
tags, **Origin/Derived links**, and Collection memberships, with actions
(add to collection, open source, delete) at hand.

## 6. Editing and vocabulary management

Adopted direction: variant B **«Edit mode + settings»**
([`prototype/editing-vocab`](https://github.com/jakebutler/inzpo/tree/prototype/editing-vocab)).

### 6.1 Edit mode

The Item detail view opens **read-only**; an explicit **✎ Edit** switches it
in place — **Done** saves, **Cancel** reverts to a snapshot. No
always-editable mode, no sheet stack.

**Edit coverage:** title, note, facet values and free tags (capture-style
trays — chips with ✕, ＋ with create-on-type), and the copied **Source** fields
(title/description/URL) edited lightly, per the glossary's "shows and edits the
copy". The Archived copy is not editable (§4.5); extracted colors are not
editable — regenerate, never hand-edit (§2.3).

### 6.2 Palette color editor

Palettes are user-owned and ordered, so their colors are hand-editable in v1 —
a full color editor: SV-drag area + hue slider; **HEX / R / G / B / C / M / Y /
K** numeric entry, all synced both ways with the picker; the 14 color-family
presets; tap-any-existing-swatch to fine-tune (live-applies); ＋ / ✕ / ‹ › for
add / remove / reorder. The color **family re-derives automatically** as colors
change (carried colors map onto the fixed taxonomy).

### 6.3 Vocabulary manager

A dedicated full-screen settings area, reached from the toolbar *and* from a
"Manage vocabulary ›" link inside edit mode. Six fixed Facets + free tags, each
with live usage counts, covering the whole lifecycle in one place: create,
rename everywhere, merge into a surviving value, remove only while unused
(§3.2). Free-tag promotion lives here too (§3.3).

## 7. Selection and bulk operations

Adopted: **explicit Selection mode on the Wall** — a **Select** toolbar button
on desktop, **long-press on a card** on mobile; taps toggle cards; an action
bar carries the count and the bulk actions.

- **Bulk tagging** — assign **and remove** facet values and free tags,
  reusing the adopted edit-mode tray components.
- **Bulk collection membership** — add + remove. Bulk-added Items **append at
  the Collection's end in the Wall's current sort order** (batch of the
  one-at-a-time behavior; reordering stays a per-Collection hand activity).
- **Bulk delete** — the item model's hard delete (§2.6) behind **one
  count-naming confirmation** ("Apply to 1,248 items?"). The **only** guarded
  bulk action: no undo system in v1; tag/collection mistakes are one inverse
  action away.
- **Select all = the whole filter-bar resolution**, not just rendered cards —
  the Wall is whatever the Filter bar resolves to, and selection semantics
  match. Bulk actions apply **server-side, count-honest**. Selection is scoped
  to the Wall, which covers Collection browsing too (a Collection is a scope
  the bar operates within).

## 8. Media pipeline

The adopted pipeline: **sharp-on-upload derivatives · per-item key prefixes ·
node-vibrant 4.x palettes · metascraper URL previews · oEmbed video posters** —
~$0/month in R2's free tier. Full research with sources:
`docs/research/media-pipeline.md` (branch `research/media-pipeline`).

### 8.1 Derivatives

**sharp on upload**, deterministically: the original is stored once and never
re-encoded; a **fixed variant set** sized to actual UI slots — `w1600` (detail),
`w640` (card), `w256` (thumb), all WebP — plus a tiny (~20–32px wide) variant
inlined as a base64 placeholder for instant grid layout. EXIF orientation is
read and normalized. Animated inputs: keep animation only in the original,
derive from the first frame. **Never rename variant keys** — add new ones and
backfill lazily; the keys double as the DB record of what exists. Lazy
on-demand generation is a future add-on, not the v1 path; CDN transforms are
unnecessary at this scale.

### 8.2 Storage layout

```
items/{ulid}/original.{ext}   # byte-exact original, immutable
items/{ulid}/w1600.webp       # derivatives; name = variant key
items/{ulid}/w640.webp
items/{ulid}/w256.webp
items/{ulid}/article.html     # an Article Item's Archived copy (§4.5)
```

- **`{ulid}`** = app-generated ULID: sorts chronologically under
  S3-lexicographic ordering, and keeps user-supplied filenames out of keys.
- **The DB is the metadata source of truth** — dimensions, sha-256, byte
  sizes, format, variant list, palette, source URL, captured preview metadata,
  timestamps. No sidecar files. Objects are addressed only by keys from the DB.
- **Capture write order**: write the DB row with a state flag → upload objects
  → flip to `ready`; a reaper deletes prefixes for rows that never became
  ready (no orphans on failed captures). Deletion: DB row → delete objects by
  prefix; retries are free.
- Store the true media type from `sharp().metadata()`, never the
  client-supplied header.

### 8.3 Color extraction

**node-vibrant 4.x** (MMCQ) on a **downscaled buffer** (sharp resize to ≤256px
long edge) for the six-swatch palette, **persisted as hex in the DB** — color
filtering (§5.3) is a DB query over stored colors, never re-extraction at
query time. **sharp `stats().dominant`** is stored alongside as the
guaranteed-populated fallback: every image Item always has at least one
searchable color even when Vibrant returns null swatches (null is a value, not
an error). Extraction is deterministic server-side — same bytes → same
palette — so a batch re-extraction with a new algorithm version is a safe
one-shot backfill.

### 8.4 URL previews

At capture for URL-linked Items:

1. **Fetch HTML** with a browser-like User-Agent, redirects followed, 10s
   timeout, hard byte cap, SSRF hygiene (no private/loopback ranges, no
   redirects into private space).
2. **Parse with metascraper** (core bundles: image, title, description, logo,
   publisher, url), resolving relative URLs against the final post-redirect
   URL.
3. **Download the preview image bytes immediately** and run them through the
   same sharp → derivatives → palette pipeline. **Never hotlink** the
   extracted `og:image` URL — signed/expiring URLs make copy-at-capture
   load-bearing (ADR-0003). Optionally retain the original og:image URL as
   provenance.
4. **YouTube/Vimeo short-circuit to oEmbed** (§8.5) — more reliable than
   scraping those pages.

**Fallbacks are first-class**: blocked fetches, SPA pages without
server-rendered OG tags (headless rendering explicitly deferred), and
non-image preview targets all leave a **valid, saved, metadata-only Item** —
the UI carries an "unfetchable but saved" state. Verify downloaded previews
decode (`sharp().metadata()`) and cap bytes.

### 8.5 Video posters

YouTube (`/oembed?url=…&format=json`) and Vimeo (`/api/oembed.json`) at
capture → store `title`, `author_name`, a **downloaded copy** of
`thumbnail_url` (through the standard pipeline), and the oEmbed `html` for the
sandboxed embed (§4.6). Use the oEmbed `thumbnail_url` field, never the
undocumented direct URL patterns. oEmbed failure (`404`/`401`/timeout) =
saved, neutral placeholder poster.

## 9. Auth — the Owner gate

Full rationale: ADR-0004.

### 9.1 The gate is app-level

Vercel Hobby's Deployment Protection covers only preview/deployment URLs —
**production domains stay public** (Password Protection is Enterprise/
Pro-add-on only). No zero-code platform gate exists at this budget; auth lives
in the Next.js app.

### 9.2 Mechanism — single high-entropy passphrase

One secret string in an env var, **timing-safe-compared** at login. No
username, no user table, no email round-trip. Rotation and recovery are the
same act: change the env var, redeploy.

### 9.3 Session — stateless, 180 days

Next.js middleware + **`jose`-signed** `httpOnly` `Secure` `SameSite=Lax`
cookie, **fixed 180-day expiry**; explicit logout just clears the cookie. No
session table in Neon, no device management in v1. ~100 lines total: roll
minimal — auth toolkits manage many users/providers and add concepts with
nothing to manage for one human. Login UX: single passphrase field
(password-manager autofill-friendly), generic error message, light rate
limiting on the login route (in-app counter or a Vercel Firewall rule,
whichever fits Hobby at build time).

### 9.4 Media sits inside the perimeter

The R2 bucket stays **private**; every image is served through an
**authenticated Route Handler** (the media proxy) with private cache headers.
This refines the storage design, not the layout: keys and derivatives are
unchanged; delivery rides behind the same gate as everything else —
unguessable keys alone are not the boundary.

### 9.5 Login preserves the destination

Login redirects back to the original destination **including query params**, so
a share-target capture opened mid-expiry lands pre-filled on the capture
surface (§4.4). Guardrail: the redirect target must be validated as a
**same-origin relative path** — no open redirect.

## 10. Stack

Full comparison matrices and sources: `docs/research/web-stack.md` (branch
`research/web-stack`); decision record: ADR-0001.

| Slot | Pick | Est. cost |
|---|---|---|
| Framework | **Next.js (App Router)** | $0 |
| Postgres | **Neon** (Free, then Launch) | $0 |
| Object storage | **Cloudflare R2** (+ sharp at capture) | $0 |
| Deployment | **Vercel Hobby** | $0 |
| **Total** | | **~$0/month** |

**Why these**: Next.js App Router maps 1:1 onto Inzpo's flows — Server Actions
for capture mutations, Route Handlers for upload → process → store and the
media proxy, `next/image` for the Wall, standardized sharp. Neon has the only
permanent free tier with scale-to-zero and PITR-style history (Supabase Free
pauses after a week idle; RDS has no permanent free tier). R2's 10 GB free
tier with **zero egress** de-risks a media-heavy vault. Vercel Hobby is
zero-config Next.js at $0.

**Caveats to carry into implementation**:

- Vercel Hobby is **personal/non-commercial** and usage-capped; a future
  commercialization forces Pro ($20/mo) or a Node-portable host (the app is
  portable by design — `next start`).
- **Neon Free suspends compute** when monthly limits are hit (hard stop, not
  overbill) and cold-starts after ~5 min idle.
- **R2 does not transform** — the design depends on capture-time sharp
  processing; Cloudflare Images (5,000 free transforms/mo) is the escape hatch
  if ever needed.
- Re-verify pricing before committing spend (figures fetched Aug 2026).

**Known library versions** (verified active, Aug 2026): sharp 0.35.4 ·
metascraper 5.56.2 · node-vibrant 4.0.4. Avoided as stale: `get-image-colors`,
`@ffmpeg-installer/ffmpeg`.

## 11. Out of scope for v1

Ruled out by the map; listed here so nobody re-litigates:

- **Auto-tagging** — post-MVP; tooling already decided (Gemini 3.5 Flash-Lite
  via Google AI Studio free tier; project + API key provisioned).
- **Palette generation via Huemint** — future development; public API decision
  recorded on the map (`POST https://api.huemint.com/color`; non-commercial,
  as-is, no uptime guarantee). v1 palette work stays deterministic extraction.
- **Multi-user accounts, sharing, public collections** — Inzpo is a personal
  vault.
- **Deeper grouping** — nested collections, board layouts, gallery views; the
  Filter bar is the auto-group.
- **Native mobile apps** — mobile-friendly web only.
- **Offline sync / multi-device conflict resolution.**
- **Importing from other tools** (Pinterest, Eagle, Pinboard, bookmarks).
- **Monetization.**
- **Similarity search** — open post-v1 sketch
  ([#11](https://github.com/jakebutler/inzpo/issues/11)); does not block
  anything here.
- **Retroactive dedup** — duplicates view, merge-Items, perceptual hashing
  (§4.2); capture-time Duplicate notice only.
- **Raw video uploads, ffmpeg/frame grabs, headless rendering for SPA
  previews, article body in Text search, multi-image share capture,
  importable Shortcuts** — deferred by §4–§5, §8 decisions with their escape
  hatches noted inline.
